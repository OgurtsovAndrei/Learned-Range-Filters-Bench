# ERE vs ERE One-D — Cache Performance Report

**Дата:** 2026-05-20  
**Машина:** Linux 6.17, x86-64 (62 GB RAM)  
**Измерение:** `perf_event_open`, user-space PMU (exclude\_kernel, perf\_event\_paranoid=2)  
**Запросов:** 100 000 (warmup: 10 000)  
**Длина диапазона:** 4 096  
**Сырые данные:** [ere_cache_2026-05-20.json](ere_cache_2026-05-20.json)

## Конфигурация

| Вариант | Структура | Векторов |
|---|---|---|
| `ere` | Два вектора: D1 (occupancy bitvec) + D2 (size encoding) | 2 |
| `ere_one_d` | Один вектор: D с кодированием Elias-Fano | 1 |

**Гипотеза (ere.tex §4):** One-D улучшает cache-локальность, т.к. cache line, загруженная первым вызовом `Select`, обслуживает последующие вызовы того же запроса.

N sweep: {2²⁰, 2²⁴, 2²⁸} = {1M, 16M, 268M} ключей.  
Датасеты: uniform, clustered (8 кластеров, σ=10%), sosd\_fb, sosd\_wiki, sosd\_osm, sosd\_books.  
Fb/wiki/books (capacity 200M) пропущены на N=2²⁸.  
Wiki\_ts: ~90M уникальных из 200M записей; загружается сколько удаётся.

## Анализ: где one-D помогает, а где нет

### Инструкции на запрос (instrs/q)

| Dataset | Изменение instrs/q | Тренд |
|---|---|---|
| uniform    | 1462 → 625  | **−57%** (стабильно на всех N) |
| clustered  | 4025–5017 → 2941–3084 | **−38–45%** |
| sosd_osm   | 4226–4438 → 2913–3091 | **−27–34%** |
| sosd_fb    | 2354–2683 → 2483–2887 | **+5–8% (ХУЖЕ)** |
| sosd_wiki  | 2338–2652 → 2647–3383 | **+0–45% (ХУЖЕ)** |
| sosd_books | 2352–2688 → 3551–3963 | **+47–51% (ХУЖЕ)** |

**Вывод:** one-D стабильно выигрывает на synthetic и OSM (монотонно возрастающие ключи с хорошим покрытием). Для fb/wiki/books — регрессия по instrs. Причина: у этих датасетов специфичная структура сегментов ERE, при которой Elias-Fano SELECT на объединённом D-векторе выполняет больше шагов, чем два отдельных SELECT по D1/D2.

### LLC промахи на запрос

| Dataset | N=2²⁰ | N=2²⁴ | N=2²⁸ |
|---|---|---|---|
| uniform   | −62% | −19% | −50% |
| clustered | +13% | −19% | −4%  |
| sosd_fb   | +433% (!) | +3% | — |
| sosd_wiki | −83% | +16% | — |
| sosd_osm  | +13% | −12% | −7% |
| sosd_books| +67% | −5%  | — |

LLC промахи при малом N нестабильны — фильтр целиком помещается в LLC, шум PMU велик относительно абсолютного значения (<1 промах/запрос). При N=2²⁴–2²⁸ картина репрезентативна.

### L1 загрузки на запрос

One-D стабильно даёт меньше L1 загрузок для uniform (−71%) и clustered (−30–50%). Для fb/books — L1 загрузок БОЛЬШЕ (+6–60%), что коррелирует с ростом instrs.

## Ключевые выводы

1. **Uniform distribution: one-D = строгое улучшение.** −57% instrs, −50% LLC miss (N=2²⁸). Алгоритмически оптимально.

2. **Real datasets (fb/wiki/books): one-D хуже по instrs.** Причина в распределении ключей — у этих датасетов ERE строит сегменты с определённой структурой gap'ов, при которой Elias-Fano SELECT по объединённому D неэффективен.

3. **OSM: умеренное улучшение.** −27–34% instrs, LLC промахи ±10%. OSM — пространственные ключи, близки к uniform по характеру.

4. **Кластеризованные ключи: instrs −38–45%, LLC промахи −4–19%.** Длинные плотные пробеги смягчают cache-эффект.

5. **Гипотеза ere.tex §4 подтверждена для synthetic/OSM, опровергнута для fb/wiki/books.** Утверждение "one-D always improves cache locality" требует уточнения в тексте.

## Рекомендация для тезиса

В ere.tex §4 стоит уточнить: "для равномерных и пространственных распределений one-D layout снижает число инструкций на запрос на 27–57%; для датасетов с кластеризованной структурой (fb, books, wiki) эффект нейтральный или отрицательный из-за увеличения сложности SELECT в объединённом векторе."
