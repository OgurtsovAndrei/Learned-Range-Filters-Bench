# ERE vs ERE One-D — Cache Performance Report

**Date:** 2026-05-20  
**Machine:** Linux 6.17, x86-64 (62 GB RAM)  
**Measurement:** `perf_event_open`, user-space PMU (exclude\_kernel, perf\_event\_paranoid=2)  
**Queries:** 100 000 (warmup: 10 000)  
**Range length:** 4 096  
**Raw data:** [ere_cache_2026-05-20.json](ere_cache_2026-05-20.json)

---

## Setup

| Variant | Layout | Vectors |
|---|---|---|
| `ere` | Two-vector: D1 (occupancy bitvec) + D2 (size encoding) | 2 |
| `ere_one_d` | One-vector: single D with Elias-Fano encoding | 1 |

**Hypothesis (ere.tex §4):** One-vector layout improves cache locality because cache lines loaded by the first `Select` call are likely to serve subsequent calls in the same query.

N sweep: {2²⁰, 2²⁴, 2²⁸} = {1M, 16M, 268M} keys.  
Datasets: uniform, clustered (8 clusters, σ=10%), sosd\_fb, sosd\_wiki, sosd\_osm, sosd\_books.  
Fb/wiki/books (200M capacity) skipped at N=2²⁸.  
Wiki\_ts: ~90M unique keys out of 200M raw entries; loads whatever dedup yields.

## Analysis: Where One-D Helps and Where It Does Not

### Instructions per query

| Dataset | instrs/q change | Direction |
|---|---|---|
| uniform    | 1462 → 625  | **−57%** (stable across all N) |
| clustered  | 4025–5017 → 2941–3084 | **−38–45%** |
| sosd_osm   | 4226–4438 → 2913–3091 | **−27–34%** |
| sosd_fb    | 2354–2683 → 2483–2887 | **+5–8% (WORSE)** |
| sosd_wiki  | 2338–2652 → 2647–3383 | **+0–45% (WORSE)** |
| sosd_books | 2352–2688 → 3551–3963 | **+47–51% (WORSE)** |

One-D consistently wins on synthetic and OSM (monotonically growing keys with good coverage). For fb/wiki/books it regresses on instructions. The cause: these datasets produce ERE segment structures where Elias-Fano SELECT on the merged D-vector requires more steps than two separate SELECTs on D1/D2.

### LLC misses per query

| Dataset | N=2²⁰ | N=2²⁴ | N=2²⁸ |
|---|---|---|---|
| uniform   | −62% | −19% | −50% |
| clustered | +13% | −19% | −4%  |
| sosd_fb   | +433% (!) | +3% | — |
| sosd_wiki | −83% | +16% | — |
| sosd_osm  | +13% | −12% | −7% |
| sosd_books| +67% | −5%  | — |

LLC miss counts at small N are noisy — the filter fits largely in LLC, absolute miss counts are <1/query. N=2²⁴–2²⁸ results are representative.

### L1 loads per query

One-D consistently reduces L1 loads for uniform (−71%) and clustered (−30–50%). For fb/books the L1 load count is higher (+6–60%), correlated with the instruction regression.

---

## Key Findings

1. **Uniform: one-D is a strict improvement.** −57% instrs, −50% LLC miss at N=2²⁸. Algorithmic win, N-invariant.

2. **Real datasets (fb/wiki/books): one-D is worse on instructions.** The key distribution produces ERE segments with a gap structure that makes Elias-Fano SELECT on the merged D more expensive than two separate SELECTs.

3. **OSM: moderate improvement.** −27–34% instrs, LLC misses ±10%. OSM spatial keys behave close to uniform.

4. **Clustered: instrs −38–45%, LLC miss −4–19%.** Long dense runs reduce the cache-line reuse benefit.

5. **Hypothesis (ere.tex §4) confirmed for synthetic/OSM, refuted for fb/wiki/books.** The claim "one-D always improves cache locality" requires qualification in the thesis text.

---

## Recommendation for Thesis

In ere.tex §4, qualify the claim: "For uniform and spatial distributions, the one-vector layout reduces instructions per query by 27–57%; for datasets with clustered structure (Facebook user IDs, book popularity, Wikipedia timestamps) the effect is neutral or negative, as the merged D-vector increases the cost of Elias-Fano SELECT relative to the two-vector baseline."
